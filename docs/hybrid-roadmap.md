# Jev 草稿模型与 Pikafish 目标搜索路线

## 当前融合协议

运行时只使用 Python 与原生 C++ Pikafish，不经过 JavaScript 搜索：

1. Python/PyTorch Jev 模型为全部合法着法给出概率。
2. 取 Top-K 草稿，Pikafish 用受限 MultiPV 搜索验证，并把结果保留在置换表中。
3. Pikafish 在剩余时间内重新搜索全部合法着法，可以接受、修正或完全拒绝草稿。
4. 模型推理、合法着法生成和两次目标搜索共享同一个墙钟预算。

该协议保留了 speculative decoding 的两个核心性质：草稿负责提出高概率候选，目标负责验证；目标始终保留回退到完整候选集的能力。棋类搜索没有 token 采样中的逐 token 分布恒等保证，因此胜率必须通过固定时间对局验证，不能从离线吻合率推断。

## 已确认的差距与解决方案

### 1. Jev 中局 Top-1 仍低

150,000 个固定 250,000 节点的中局教师样本，将严格、按对局隔离的 Top-1 从 24.10% 提高到 30.42%，但旧独立测试退化。这说明数据域覆盖和连续变化学习都是瓶颈。

解决方案：

- 混合旧独立棋谱与新 CCPD 固定节点样本，训练时按数据源加权，验证时同时设置新、旧两个晋升门槛。
- 将 Pikafish 完整 PV 展开为后续局面监督，让模型学习连续应对，而不只拟合根节点标签。
- 保留 MultiPV 分数，以排序损失和概率蒸馏共同训练；对前两名分差很小的局面降低硬 Top-1 权重。
- 扩展至更多互不重复的对局和局面，保持按整局切分，杜绝同局泄漏。

### 2. 草稿置信度没有参与预算分配

固定 Top-8、固定 15% 验证时间会在高置信度局面上浪费候选，在低置信度局面上覆盖不足。

解决方案：

- 根据累计概率选择动态 K，并设置最小 4、最大 16。
- 根据策略熵和第一、第二候选概率差动态分配 5% 到 20% 的验证时间。
- 当模型置信度很低时跳过受限搜索，把全部预算交给完整 Pikafish。
- 用固定开局的成对对局选择参数，不用训练集 Top-1 直接决定参数。

### 3. 两阶段搜索存在重复启动成本

当前协议依赖两次 UCI `go`。置换表可以复用，但迭代加深和根节点准备会重复执行。

解决方案：

- 下一版给 Pikafish 增加只影响排序、不删除合法着法的 `DraftOrder` 根节点提示。
- Jev 概率用于根节点及低层节点排序；Alpha-Beta 仍搜索全候选集。
- 对照现有两阶段协议，比较相同时间内的节点数、完成深度、选择深度和胜率。

### 4. 局面价值和战术标签不足

单纯模仿最佳着法无法解释候选为什么失败，也不能稳定预测深层战术后果。

解决方案：

- 同时蒸馏 Pikafish 的 cp/WDL、最佳着法、MultiPV 分差和完整 PV。
- 对将军、吃子、唯一应手、弃子和长将局面提高抽样权重。
- 价值网络用固定节点标签与终局结果联合训练，并分别报告开局、中局、残局误差。
- 只有在对局隔离测试和固定时间成对比赛都进步时才替换生产模型。

### 5. 评测样本量不足

少量对局只能用于发现程序错误，不能证明棋力提升。

解决方案：

- 第一阶段用 5 秒/步、固定开局、红黑互换的 10 局验证方向。
- 后续扩大到至少 100 个成对对局，报告胜和负、置信区间和 Elo 区间。
- 每次保存 Pikafish、NNUE、Jev 模型的 SHA-256，以及线程、哈希、时间、Top-K 和验证比例。
- 对参数优化和最终确认使用不同开局集合，避免在比赛集上调参。

## 晋升门槛

融合引擎或新 Jev 模型必须同时满足：

1. 对局隔离的中局固定节点 Top-1 不低于当前生产模型，并最终达到 50%。
2. 旧独立中局测试不得明显退化。
3. 固定 5 秒成对比赛对原生 Pikafish 的结果不劣于对照，扩大样本后置信区间支持提升。
4. 每步墙钟时间包含草稿推理和目标验证，不允许给融合引擎额外时间。
